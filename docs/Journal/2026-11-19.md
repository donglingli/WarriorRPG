- 实验 2（构造与析构顺序）要回答的问题：

预测：ctor GlobalTracer  -> ctror LocalTracerA -> ctor LocalTracerB ->  ctor NewAndNotDeleteTracer -> ctor NewAndDeleteTracer -> dtor NewAndDeleteTracer -> dtor NewAndNotDeleteTracer -> dtor LocalTracerB -> dtor LocalTracerA -> dtor GlobalTracer

## 段 1 结论（过线）

**规则两条**（MSVC 默认，标量类型）：
1. 每个成员的起始偏移 = 它自身对齐数的整数倍，不足则在前一个成员之后插填充。
2. struct 总大小 = 最大成员对齐数的整数倍，不足则在末尾补填充。

**三个量别混**：成员大小（体宽） / 偏移差（间距，含填充） / sizeof（总量，含尾部补白）。

| 案例 | sizeof | 填充位置 |
|---|---|---|
| `char int char` | 12 | a 后 3，c 后 3（尾部） |
| `char char double` | 16 | 第二个 char 后 6 |
| `char int double` | 16 | a 后 3 |
| `char int double char` | 24 | a 后 3，**第四个成员 d 之后** 补 7 |

> 边界：`#pragma pack(n)` / `/Zp` 会改对齐数；UE 的 `USTRUCT` 含 `UPROPERTY` 与 GC 字段，布局不能直接套这套规则。这两条留到 Week 1 后半段。

## 段 2 结论（过线）

**三个词必须分开用**：

| 词 | 结束时刻 | 谁负责 |
|---|---|---|
| 变量 `p` 的作用域 | `}` | 编译器，自动 |

**四个已验证的观察**（都是自己跑出来的）：

## 段 3 结论

**A. 未初始化成员在 UObject 里是零**（【验证】，不是推理）

```
LogTemp: Warning: ProbeInt=0  ProbeObj=nullptr
```

`UPROPERTY() int32 ProbeInt;` 没写初始化，`UObject*` 也没写 `= nullptr`，两者都打印出 0 / nullptr。

**原因**：引擎分配 UObject 内存时（`StaticAllocateObject` → `GUObjectAllocator`）先把整块内存清零，然后才跑构造函数。

| 场景 | 未初始化成员指针的初值 |
|---|---|
| 普通 C++ 类（`F:\CPP_Lab` 里已验证） | **垃圾值** |
| UObject 派生类 | **nullptr**，因为内存先被清零 |

> 同一句代码两种规则，差别不在语法，在**谁分配内存**。

**B. 构造函数执行次数：名字就是身份**（【验证】—— 在 BP 编辑器里点一次「编译」采集到）

```
ctor: Default__SKEL_BP_HeroCharacter_C      isCDO=1   ← 骨架类 CDO
ctor: Default__BP_HeroCharacter_C           isCDO=1   ← 真正类 CDO
ctor: BP_HeroCharacter_C_0                  isCDO=0   ← 已存在实例被重建
ctor: BP_HeroCharacter_C_1                  isCDO=0   ← 已存在实例被重建
ctor: BP_HeroCharacter_C_2                  isCDO=0   ← 已存在实例被重建
```

**点一次「编译」，构造函数跑了 5 次。** 而这次操作没有创建任何新角色、没有进游戏。

| 名字 | 是什么 | 为什么存在 |
|---|---|---|
| `Default__SKEL_BP_HeroCharacter_C` | **骨架类**的 CDO | 编辑器专用，给蓝图编辑器编译时自己用 |
| `Default__BP_HeroCharacter_C` | **生成类**的 CDO | 运行时的类默认对象 |
| `BP_HeroCharacter_C_0 / _1 / _2` | 实例 | **重新实例化**：编译生成新 UClass 后，旧实例被重建以换用新类 |

> **结论**：构造函数会为"类"执行（而且是**两个**类），也会为"被重建的旧实例"执行。
> 所以构造函数里只能放默认值设定和 `CreateDefaultSubobject`，**任何有副作用的代码都会被放大 5 倍**——而玩家什么都没做。
>
> 这就是 UE 必须有 `BeginPlay()` 的原因：**构造函数负责"造出来"，`BeginPlay` 负责"进入世界"。**
> 同一道理：上午 `GlobalTracer` 构造在 `main` 之前 —— **对象存在 ≠ 对象可用**。

# Day 2 · 成员函数怎么找到对象；虚函数为什么让对象变大

> 语料：`F:\CPP_Lab`（exp03 / exp04） + `Warrior` 技能继承链（只读）

## 开工（先答，不许查资料）

> 一个类的成员函数，存在对象的哪个字节里？

我答不上出来，不明白为什么叫做对象的哪个字节，function字节吗【猜】

**批注**：这是一道**陷阱题**，正确答案是「它不在对象的任何字节里」。答不上来是预期结果，不是失败。
「function 字节」这个说法暴露了混淆：**函数没有“字节”这个量**。`sizeof(Point::Print)` 是编译错误，不是返回 0 —— 这个量根本不存在。

## 段 1 结论 · this 指针

**押注**（写死后再跑）：
- `sizeof(Point)` = 8，依据：两个int 4+4=8
- 加两个成员函数后，`sizeof` 变了没有？ 【猜】加了函数，sizeof没有变；
- `&p` 与 `this` 相同还是不同？【猜】相同，都是同一个对象

**实测**（4 个改动实验）：

| # | 改动 | 结果 |
|---|---|---|
| 1 | 成员函数里修改 `x`，外部重新读取 | 读到的是新值 —— 说明 `this` 指向真实对象，不是副本 |
| 2 | 给 `PrintByMember` 加 `static` | 不能访问 `x` / `y`，编译错；在结构体内定义 `static int` → **LNK2001** |
| 3 | 加到 1000 个成员函数 | `sizeof` 依旧不变 |
| 4 | 返回 `this` 链式调用 | 与前面结果一致 |

**我的解释**：
增加成员函数不改变对象大小；`this` 指向对象的首地址，也就是 `&p`。

> **一处必须纠正**：「`this` 在对象内部」这个说法错了。指向对，位置错 —— 见下方批注。

**批注 · this 不在对象里**
`p.Print()` 被编译成 `Print(&p)`：`this` 是编译器**隐式加的一个参数**，走寄存器（MSVC x64 是 `RCX`）或栈，与对象内存无关。
反证：`sizeof(Point)` 是 8。若 `this` 是对象成员，x64 下至少多 8 字节，`sizeof` 该是 16。

**批注 · LNK2001 是意外收获（Week 3 地基）**
类内 `static int count;` 只是**声明**，不分配空间；必须在类外**定义**一次（C++17 前）：
```cpp
int Point::count = 0;   // 这一行才分配存储
```
「声明 ≠ 定义」这条线，直接通向 Day 3 的 `LNK2019`。

**批注 · static 成员的存储位置（【验证】）**

| 打印对象 | 地址 | 区段 |
|---|---|---|
| 函数 `RunExp05` | `00007FF63A151424` | `.text`（代码段） |
| `Point::count` | `00007FF63A161000` | `.data`（数据段） |
| `new Point` | `000001381DFA2C70` | 堆 |

函数与 static 成员同前缀 `00007FF6`，两者相差 `0xFBDC` ≈ **63 KB** —— 同一个 exe 映像内的相邻段。
堆地址前缀 `00000138`，完全另一个区段。

**结论**：`static` 成员与代码住在一起，映像加载时它就在，映像卸载时才消失。**不在堆上。**

另一面：`static` 成员函数不能用 `this`（段 1 第 2 条改动）。
**没有 `this` → 不属于任何对象 → 不占对象大小 → 不需要每对象一份 → 只能放在类级别的位置**。这四步是同一条链。

## 段 2 结论 · 虚函数与对象大小

**sizeof 数据**（每条只改一个变量）：

| 版本 | sizeof | 判定 |
|---|---|---|
| `{ int a; }` 无虚函数 | 4 | ✅ |
| `{ virtual f; int a; }` | 16 | ✅ 数字对，**布局推理错**（见下） |
| 3 个虚函数 + `int a` | 16 | ✅ 加虚函数不改变对象大小 |
| 只有虚函数、无成员 | 8 | ✅ vptr 本身 = 8 |
| 去掉 `virtual` | 4 | ✅ |
| 纯虚函数 | 16（不变） | ✅ 只影响 vftable 槽位 |
| `Derived : Base { int b; }` | 24 | ✅ |
| `Derived2 : Derived`（不加成员） | = `Derived` | ✅ 继承不新增 vptr |

> 原始自我发现：「我总下意识的想着偏移是从 0 + 变量自身大小」—— 所以预测 `a` 在偏移 4，实测 **8**。

**编译器裁决（`cl /c /d1reportSingleClassLayoutBase`）**：

```text
class Base      size(16):
0      | {vfptr}
8      | a
| <alignment member> (size=4)      ← MSVC 自己标出的补白

Base::$vftable@:
| &Base_meta                        ← vftable[-1]，RTTI 指针
0      | &Base::Speak
1      | &Base::Walk
2      | &Base::ab
```

**三个虚函数 → vftable 三个槽位，但对象里只有一个 `{vfptr}`。**

**vptr 为什么必须在偏移 0**：
每次虚调用 = 「对象地址 + 0」取出 vptr，一条 `mov` 就完成；放别处则每次多一次加法。MSVC 与 GCC 都遵循这条 ABI。

**Derived = 24 的原因**：
`vptr 8 + a 4 = 12` → `Base` 尾部补到 16；MSVC **不复用**这 4 字节补白，`b` 从 16 开始，末尾再补到 24。
若复用（GCC/Clang 的 Itanium ABI），结果是 **16**。同代码不同 `sizeof`，这是最常见的原因之一。

**我的解释**（每对象一份 / 每类一份）：
- **每个对象一份**：`vptr` —— 8 字节，偏移 0
- **每个类一份**：`vftable` —— N 个虚函数 → N × 8 字节，放在 `.rdata`（和昨天的 `static` 同一个区域）
- 加虚函数 → vftable 变长，**对象不变大**；查表按下标取一次，O(1)，不随虚函数数量变慢
- `this adjustor: 0` —— 单继承不需要调整 `this`；多继承时这个字段才非零

**判定：方向对，覆盖了七成。**

说对的两条：
- **契约被稀释**：基类一旦暴露 `GetHeroCombatComponent()`，等于向所有子类承诺"你能拿到 Hero 的战斗组件"。Enemy 兑现不了，调用方就无法信任基类接口 —— 这才是"失去继承意义"的准确含义。
- **回归范围扩大**：改一次要测 Hero 全链 + Enemy 全链，哪怕 Enemy 根本不该走这条路径。

**补上漏掉的一层：错误会从编译期掉到运行期。**

你原话假设了"使用时需要判断"。但现实里更常见的是：

```cpp
// 基类
virtual UWarriorHeroCombatComponent* GetHeroCombatComponent() const { return nullptr; }
```

这行能编译通过。Enemy 的 GA 不覆写，照样继承到一个返回 `nullptr` 的版本。于是有人写：

```cpp
GetHeroCombatComponent()->GetCurrentWeapon();   // 编译过，运行崩
```

**编译器不会报错，因为类型完全合法。** 你损失的不是"一个 if"，是**编译器帮你拦的那道关**。

> 函数放哪一层，本质是在选「让编译器拦」还是「让运行时拦」。四道关卡，越往后代价越高。

**③ 四道关卡（今晚用两行代码实测出来）**

| 关卡 | 谁在拦 | 错误码 | 编译器知道什么 | 不知道什么 |
|---|---|---|---|---|
| 1 作用域查找 | 编译期 | `C3861` 找不到标识符 | 什么都不知道 | 这个名字属于谁 |
| 2 成员查找 | 编译期 | `C2039` 不是 X 的成员 | 类型存在 | 类型里有这个成员 |
| 3 符号链接 | 链接期 | `LNK2019` / `LNK2001` | 声明存在 | 实现在哪 |
| 4 运行 | 运行时 | 崩溃 | 全部存在 | 语义对不对 |

**两条实证**（都在 `WarriorEnemyGameplayAbility.cpp` 里制造）：

```cpp
GetHeroCombatComponent();            // → C3861 找不到标识符（第 15 行）
FakeHero->GetHeroCombatComponent();  // → C2039 不是 UWarriorHeroGameplayAbility 的成员（第 17 行）
```

同样是"找不到"，写法不同、查找路径不同、报错不同：

- 非限定名 `Foo()` → 查**作用域链**（Enemy → UGameplayAbility → UObject，够不到 Hero）→ `C3861`
- 成员访问 `obj.Foo()` → 查**类型的成员表** → `C2039`

> `C2039` 出现时，编译器并没有确认"这个名字在别处存在"，它只说"这个类型里没有"。
>
> 顺带：Day 2 段 1 的 `LNK2001` 和这里的 `C3861` 是同一条线索的两端 ——
> **`LNK2001` 是认识名字、找不到实现；`C3861` 是根本不认识名字。**

**④ 今晚的预测-实测记录**

| 轮次 | 预测 | 实测 | 结论 |
|---|---|---|---|
| 1 | 编译器报错，"没有定义" | `C3861` 找不到标识符 | 方向对，措辞要改：不是"没定义"，是"没声明/没进作用域" |
| 2 | `C2039` 没有该成员 | `C2039` 不是成员 | 完全吻合 |

## 我预测错了的地方（最重要的一栏）

1. **我以为「成员函数占对象的字节」**，所以看题时想到「function 字节」。实际函数根本不在对象里，`sizeof` 也不接受函数。段 1 的三条预测（8 / 不变 / 相同）反而全对 —— 说明我知道结果，但不知道为什么是这个结果。
2. **我把 `this` 当成了对象内部的成员。** 实际它是隐式参数，走寄存器/栈，不在对象内存里。这个错的代价：以后解释 `sizeof` 反常时会漏掉这一项。
3. **我看到三个地址，判断「static 变量的地址和 new 出来的差不多，所以在堆上」。** 实际三个地址落在三个完全不同的区段：
   - `0000005E2D8FF528`（栈对象）
   - `000002140D6C2C70`（堆对象）
   - `00007FF6013E1000`（模块数据段）

   一个都不接近。**「差不多」是个危险词** —— 它让一个可以被推翻的判断（差 5 个数量级）变成了一句无法反驳的观感。这是「观察和解释混在一起」的升级版：这次连观察本身都不准。
4. **我把 `C3861` 说成了"没有定义"。** 实际是"名称查找失败"，发生在编译期最早一步，连类型检查都没到。`LNK2001` 才是"没定义"。两个词混用，等于把两道关卡当成一道。
5. **我以为"函数放错层"的代价是"多写一个 if"。** 实际代价是：错误从编译期掉到运行期，从"红波浪线"变成"线上崩溃"。
