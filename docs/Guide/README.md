# 记录规则

这里规定 `Docs/` 下每份文档怎么写、什么时候写、写到什么程度算合格。

**规则存在的原因**：不设规则的记录会退化成「流水账」或「什么都不写」，两种都白费时间。

---

## 一、目录职责

| 路径 | 放什么 | 频率 |
|---|---|---|
| `Journal/` | 每日笔记，文件名 `YYYY-MM-DD.md` | 每天 |
| `DesignDecisions.md` | 设计判断台账：我为什么这么设计 | 有感就加，目标 30 条 |
| `Bugs/` | 踩坑记录，文件名 `YYYY-MM-DD-英文短名.md` | 每踩一个坑 |
| `Experiments/` | 实验结论与数据（bench 数字、布局打印、编译耗时） | 每周 |

**文件名一律 ASCII**（日期 + 英文短名），内容写中文。避免跨平台与 git 的编码问题。

---

## 二、和 `PROGRESS.md` 的区别

| | `PROGRESS.md` | `Docs/Journal/` |
|---|---|---|
| 记什么 | **做了什么** | **理解了什么** |
| 形态 | 进度流水账 | 有档位、有验证方式、有悬着的疑问 |
| 给谁看 | 未来的自己找回上下文 | 面试与复盘 |

两份都要，不要合并。混在一起的结果是两个目的都达不到。

---

## 三、每日笔记：固定六行

收工时填，格式固定，多一行都不要：

| 概念 | 代码里的对应物 | 我怎么验证的 | 档位 |
|---|---|---|---|

- **概念**：今天真正搞懂的一个点，一句话
- **代码里的对应物**：落到具体的类名 / 函数名 / 行
- **我怎么验证的**：跑了什么、看到了什么输出
- **档位**：见下节

再加两栏必填：

- **我预测错了的地方** —— 这栏比其余所有栏加起来都值钱
- **悬着的疑问** —— 至少 1 条，并写清「明天怎么验证它」

**六行里至少有一行是【验证】。** 全是【猜】和【依据】，说明今天只输入没输出。

---

## 四、档位（说结论前必须先标）

| 档位 | 含义 | 是否过线 |
|---|---|---|
| 【猜】 | 没有依据，凭直觉 | 允许，但不算过线 |
| 【依据】 | 读过文档或源码，能说出去处 | 半过，会被追问「哪一节」 |
| 【验证】 | 自己跑过实验，有输出或数字 | 过线，**只有这一档能写进简历** |

**允许猜，但不允许把猜说成知道。** 面试官最怕的不是「不会」，是 confidently wrong。

---

## 四之二、工作台「卡点」栏怎么写

**这一栏只写「我现在还答不上来的问题」，写成疑问句，最多 3 条。**

```
✅ 1. FORCEINLINE 和 inline 到底差在哪？编译器听谁的？
   2. GENERATED_BODY() 展开了什么？

❌ 1. 一开始 struct 大小预测错了，9 次修改后理解了对齐规则   ← 这是已解决的结论
   2. 理解了存储期原则，栈内存销毁不代表对象不存在           ← 这是产出
```

**为什么必须分开写**：

1. **卡点是第二天唯一的入口。** 全是「已经理解了」，第二天就不知道该从哪开始。
2. **它会让「越学越会」的错觉固化。** 一天结束时写满「理解了」，情绪上舒服，但这正是「觉得自己会了」的生成机制。

已搞懂的内容写进「今日产出」或 Journal 的结论，**不要混进卡点**。

---

## 五、commit 规则

- **一天一条 commit**，收工前提交，message 写「Day N: 今天做成了什么」
- **任何大改动之前先 commit**（改网络、改架构、动蓝图基类）
- 42 天 42 条 commit，本身就是一份成果清单

---

## 六、抽查机制

每日笔记提交后，会被从里面抽一条问「为什么」，追问两层。

答不上来 → 当天笔记作废，重写。

**目的不是惩罚，是防止「看懂了」被误当成「会了」。** 能讲清因果，才允许往下一格走。
