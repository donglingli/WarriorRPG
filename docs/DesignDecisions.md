## 001 · 连击技能为什么放在蓝图 GA 里，以及连击数该存哪

**日期**：2026-11-18　**主题**：GAS / 分层 / 状态归属

### 我原来的判断（原文）

> 【猜】这块从逻辑来看，执行频率还好，依靠按键触发，复用范围仅限于新武器复用，做完之后几乎不会变更，我觉得写在 C++ 也方便调试，做完之后派生蓝图类就好。

### 现状（事实描述）

- 输入在 C++ 绑定 → `TryActivateAbility`
- `GA_LightMaster` / `GA_HeavyMaster` 是**蓝图**，图里调用 `PlayMontageAndWait`、`WaitGameplayEvent` 编排流程
- 命中重叠处理也在蓝图，之后调 C++ 函数构造 `SpecHandle` 并应用
- 这套蓝图再作为基类，给每把武器派生一份
- **连击数是 GA 的成员变量**，实例化策略 `Instanced Per Actor`，通过 ApplySpec 时传入伤害结算

### 判定结果

| 维度 | 我的判断 | 判定 | 错在哪 |
|---|---|---|---|
| 执行频率 | 还好，按键触发 | ❌ | 混淆"激活频率"与"激活后内部执行频率"。命中检测若是 NotifyState 每帧 trace，就是最高频的一段 |
| 复用范围 | 仅新武器复用 | ❌ | 判据错了。真实判据是"多少系统要读它"：UI（连击显示/窗口倒计时）、AI、存档、网络同步——全在 C++，而蓝图类是黑盒 |
| 变更频率 | 几乎不变更 | ❌ | 把"流程"和"数值"当成一件事。段数/窗口/宽限/倍率是策划天天调的东西 |
| 调试需求 | C++ 方便调试 | ✅ | 对，但断点只占一半，另一半是 diff 可读性与 code review |

**漏掉的第五个维度：依赖方向。**
> 被依赖的东西必须在 C++。
> 要让 C++ 系统读蓝图 GA 的内部状态，只有三条路：靠 Tag 传、靠接口（无编译期约束）、或者各处重算。三条都是坑。

### 正确的切分

| 层 | 放什么 | 连击系统具体内容 |
|---|---|---|
| **C++ GA 基类** | 流程 + 状态 + 对外接口 | 段数状态机、窗口开关、输入缓存、命中结算时机、`GetCurrentComboIndex()` |
| **蓝图子类** | 只填资源引用 | 每段蒙太奇、特效、音效、是否允许位移 |
| **DataAsset** | 纯数值 | 段数上限、每段窗口时长、输入宽限、伤害倍率曲线 |

**关键更正**：蓝图在这里的角色不是"写逻辑"，是"编排 C++ 任务节点的顺序"。`PlayMontageAndWait`、`WaitGameplayEvent` 全是 C++ 的 `UAbilityTask`，那张图本质是流程图。**而流程是最稳定的部分，最该被 C++ 固化。**

### 遗留问题一：连击数的状态归属（高优先级）

`Instanced Per Actor` 本身选对了——要跨激活保持状态，这是唯一合理选择。但它带来三个必须配套处理的事：

1. **实例活到 Actor 死，成员变量不会自动清零。** 归零时机（超时 / 切武器 / 受击 / 死亡）必须显式写，否则会出现"打着打着从第 3 段开始"。
2. **状态现在有两份。** 外部算的 + GA 里存的，两份状态必然漂移。真源必须在唯一一处。
3. **它不参与复制。** GA 实例不复制，成员变量更不复制。改成 Listen Server 后，客户端预测激活 +1、服务器激活 +1、服务器若拒绝则客户端不回退 → **两端永久错位**。

**推荐做法**：连击数放进 `WarriorAttributeSet`（自动复制 + 可绑 OnRep 驱动 UI + 能直接进 GE Modifier 做段数加成）。
备选：`WarriorCombatComponent` 的 `UPROPERTY(Replicated)`；或 GameplayTag 计数（Tag 数量本身可复制）。

### 遗留问题二：服务器在信任客户端的连击数

现在是"通过 ApplySpec 传入连击数做伤害结算"。这一步本身是**对的**（`GEExecCalc_DamageTaken` 读不到 GA 成员变量，只能从 Spec 的 SetByCaller 取）。

但它意味着：**伤害高低取决于客户端声称自己是第几段，服务器无条件相信。**
单机无所谓；多人环境下这是权威性问题，是可被利用的漏洞。这正是 Week 5「权威与信任」要处理的东西。

### 遗留问题三：变更成本

我承认："改 5 段只能靠重新测试验证，无法确认没改坏前 3 段。"

**这不是测试不够勤奋，是结构决定的。**
流程写死在图里 → 段数变更等于流程变更 → 必然触发全量回归。
流程留 C++ + 段数配进 DataAsset → 加两行配置，流程代码零改动 → 前 3 段的行为由同一份数据驱动，天然不可能被破坏。

**判断标准**：能不能确认没改坏，取决于代码结构，不取决于测试强度。

### 面试怎么讲（口语版）

> "连击这块我一开始把流程放在蓝图 GA 里，每把武器派生一份。后来做网络改造时发现两个问题：一是连击数存在 GA 成员变量里，`Instanced Per Actor` 的实例不参与复制，客户端预测和服务器执行会各自递增，一旦服务器拒绝激活就永久错位；二是伤害结算靠 Spec 的 SetByCaller 把连击数传给服务器，等于服务器无条件信任客户端。
> 我的改法是把连击数挪进 AttributeSet 让它自动复制，流程收进 C++ GA 基类，只用 DataAsset 配段数和窗口时长——这样改段数不用动代码，也就不用回归前几段。"
